# BM25 — Best Match 25

## What it is

A classical sparse retrieval algorithm that scores documents by how often query terms appear in them, adjusted for document length and term rarity. The standard baseline for keyword search — used in Elasticsearch, Lucene, Solr, and Azure AI Search.

## What problem it solves

Given a query and a corpus of documents, rank the documents by relevance to the query using only exact term matching — no embeddings, no neural networks.

## Notes

### Building BM25 from intuition

Start with the simplest possible ranking: count how many times the query term appears in each document.

```
score = raw term count
```

This breaks in two ways:

1. **Long documents always win** — a 5,000-word document with 10 occurrences of "lunas" outscores a 50-word document with 5 occurrences, even though the short document is clearly more focused on the topic.

2. **Unlimited counts are misleading** — the 10th occurrence of "lunas" adds less information than the 1st. By the 50th occurrence, you already know the document is about lunas. BM25 calls this **term saturation**.

BM25 fixes both problems.

---

### Component 1 — TF with saturation and length normalization

```
TF_bm25 = (count × (k1 + 1)) / (count + k1 × (1 - b + b × doc_length/avg_length))
```

**Parameters:**
- `k1 = 1.2` — controls saturation speed (higher = slower saturation)
- `b = 0.75` — controls length normalization strength (0 = no normalization, 1 = full)

**Saturation in practice** (b=0, only saturation):

| Occurrences | TF_bm25 (k1=1.2) |
|---|---|
| 1 | 1.00 |
| 2 | 1.36 |
| 5 | 1.65 |
| 10 | 1.78 |
| 50 | 1.95 |
| ∞ | → 2.20 (ceiling = k1 + 1) |

The score approaches `k1 + 1` as a ceiling but never reaches it. The 50th occurrence adds almost nothing over the 10th.

**Length normalization:** if `doc_length > avg_length`, the denominator grows and the score drops. A document with 5 occurrences of "lunas" in 50 words scores higher than one with 5 occurrences in 500 words.

---

### Component 2 — IDF (Inverse Document Frequency)

A term that appears in every document carries no information — finding "el" in a document tells you nothing about relevance. A term that appears in few documents is highly discriminative.

```
IDF = log((N - df + 0.5) / (df + 0.5))
```

Where:
- `N` = total documents in the corpus
- `df` = number of documents containing the term

**Example with 382 chunks:**

| Term | df | IDF | Signal |
|---|---|---|---|
| "el" | 380 | ≈ -5.0 | Penalized — appears everywhere |
| "seguro" | 200 | ≈ -0.09 | Near zero — too common |
| "lunas" | 15 | ≈ 3.17 | High — domain-specific |
| "panorámicas" | 2 | ≈ 5.02 | Very high — very rare |

Terms that appear in fewer than half the corpus get positive IDF. Terms more common than that get negative IDF and are effectively ignored.

---

### Full BM25 formula

For a single term:
```
BM25(term, doc) = IDF(term) × TF_bm25(term, doc)
```

For a multi-word query, sum across all terms:
```
BM25(query, doc) = Σ IDF(term) × TF_bm25(term, doc)   for each term in query
```

**Why this works well on technical queries:** a query like *"Artículo 15 responsabilidad civil 600 €"* contains rare, specific terms with high IDF. Documents containing all of them score very high. Documents about liability in general but not article 15 specifically score lower.

---

### Where BM25 breaks down — Spanish morphology

BM25 was designed and tuned (`k1=1.2`, `b=0.75`) on English corpora. It relies on **stemming** to group word forms — stripping suffixes to match `cover`, `covered`, and `covering` to the same root.

Spanish is morphologically richer than English. The same root produces far more surface forms:

```
cubrir → cubre, cubierto, cobertura, coberturas, cubrimiento,
         cubro, cubrimos, cubrían, cubierta, cubiertos...
```

BM25's English stemmer either:
- **Doesn't stem Spanish words** → `cubre` and `cobertura` are different terms, a query with one misses documents with the other
- **Stems incorrectly** → cuts the wrong suffix, produces a non-word that matches nothing

Result: BM25's recall on Spanish text is lower than on English. Corpus-trained sparse methods (SPLADE, TF-IDF vectors) avoid this by learning from actual co-occurrence patterns — they discover that `cubre` and `cobertura` appear in similar contexts without needing a stemmer.

---

### When to use BM25

- You need a fast, no-training sparse retrieval baseline
- Your corpus is in English (you can change the stemmer)
- You're using a stack that includes it natively (Elasticsearch, Azure AI Search, Lucene)

Avoid BM25 as the sparse component of hybrid search when your corpus is in a morphologically rich language (Spanish, French, Turkish, Finnish) — use corpus-trained sparse vectors instead.
